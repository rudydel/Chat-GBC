# Architecture: a transformer on an 8-bit CPU without a multiplier

This document explains how the Game Boy runs the model and why the design
looks the way it does. `llm/simulate.py` is the executable version of this
document: every formula below is one line there and one line in
`gb/src/llm.c`.

## 1. The constraints

| Resource | Original Game Boy (DMG) | Consequence |
|----------|-------------------------|-------------|
| CPU | Sharp SM83, 8-bit, ~1.05 M cycles/s (4.19 MHz / 4), **no multiply instruction** | multiplications become table lookups |
| Work RAM | 8 KiB (minus stack) | activations only; the KV cache does not fit |
| Cartridge SRAM | 8 KiB banks, up to 128 KiB on MBC5 | KV cache lives here, two banks per layer |
| ROM | 16 KiB banks, up to 8 MiB on MBC5 | weights (int7) plus code |
| Screen | 20 × 18 tiles of 8 × 8 pixels, 4 shades | a 20-column text terminal |

## 2. The model

A pre-norm GPT with no biases, RMSNorm (gains folded into the next linear
layer), ReLU feed-forward and learned position embeddings:

```
h   = tok_emb[t] + pos_emb[p]                     int16 residual, value = h * 2^-e_res
for each layer:
    n   = int7( h / rms(h) * 2^4 )                 RMSNorm, output exponent E_NORM = 4
    q,k,v = int7( n @ Wq >> s_q ), ...             int7 weights, per-tensor power-of-two scale
    o   = int7( softmax(q k^T / sqrt(16)) v )      exp table, 7-bit weights, division per output
    h  += int7( o @ Wo >> s_ao ) << rs_a
    n2  = int7( h / rms(h) * 2^4 )
    f   = int7( relu(n2 @ W1) >> s_f )             values 0..63
    h  += int7( f @ W2 >> s_fo ) << rs_f
logits = int7( h / rms(h) * 2^4 ) @ Wlm           int32, argmax or sampled
```

Character-level vocabulary of 54 tokens (`llm/tokenizer.py`): 4 specials
(`<pad> <eos> <usr> <bot>`), space, a–z, 0–9 and 13 punctuation marks. A
conversation is `<usr> question <bot> answer <eos>`. By default the ROM
starts a fresh context for every question; built with `-DKEEP_CONTEXT`
(`EXTRA_CFLAGS=-Wf-DKEEP_CONTEXT`) it keeps the whole conversation in the
KV cache until the context (128 tokens) would overflow. The model is
trained on packed multi-turn windows either way, but with 48k parameters
earlier turns hurt more than they help (measured exact recall on the
shipped model: 95% fresh vs 62% multi-turn).

Default size (`configs/tiny.json`): d_model 48, 2 layers, 3 heads of 16,
d_ff 96, context 128 → 48,432 parameters, ~40k multiply-accumulates per
token plus attention.

## 3. Number formats

* **int7**: integers in [-63, 63]. Weights, all activations, softmax
  weights. Stored *biased* as bytes `value + 63` (0..126) wherever the asm
  dot product reads them.
* **Power-of-two scales**: a tensor with exponent *e* holds `real * 2^e`.
  Weight exponents come from the max-abs of each tensor; activation
  exponents from an exponential moving average of the max-abs seen during
  training (`ActQuant` in `llm/model.py`). Because all scales are powers of
  two, requantizing an accumulator is a single right shift `s`, and the
  exporter checks `0 <= s <= 24`.
* **Residual stream**: int16 with exponent `e_res` (10 by default, so 1.0 =
  1024). Block outputs are int7 with an exponent in `[e_res-8, e_res]` so the
  add `h += a << rs` never overflows more than the saturation handles.
* **Accumulators**: 24/32-bit.

Quantization-aware training applies exactly these roundings (straight-
through estimator), which is why the integer model tracks the float model
closely (argmax agreement on essentially every step; logit error ≈ 1%).

## 4. Multiplying without a multiplier

For a weight row `w` and activation vector `x` (both int7):

```
sum_i w_i x_i = ( sum_i (w_i + x_i)^2  -  sum_i w_i^2  -  sum_i x_i^2 ) / 2
```

`sum_i w_i^2` is precomputed per row at export time (4 bytes per row in
ROM; for cache rows it is computed when the row is appended). `sum_i x_i^2`
is computed once per vector (cheap: a 127-entry square table). The
remaining term needs only additions and a lookup in a 253-entry table
`SQ[k] = (k - 126)^2` indexed by the byte `wb + xb` (both biased, so the
index is 0..252 and never carries).

`gb/gen/dot_gen.s` is generated by the exporter and fully unrolled. It
points the **stack pointer** at the weight row and `pop`s two weights per
instruction (3 cycles for 2 bytes), reads `x` from fixed addresses, and
accumulates the 16-bit table entries into a 24-bit register accumulator.
Per element: ~22 cycles. Interrupts are disabled while SP is redirected
(≤ 3 ms per row).

```
        pop  bc              ; c = w[i], b = w[i+1]
        ld   e,b
        ld   a,(_xvec+i)     ; x[i]
        add  a,c             ; table index
        ld   c,a
        ld   b,#>_sq_tbl     ; low-byte page of the table (0x3E)
        ld   a,(bc)          ; SQ low byte
        add  a,l
        ld   l,a
        inc  b               ; high-byte page (0x3F)
        ld   a,(bc)
        adc  a,h
        ld   h,a
        jr   nc,1$
        inc  d               ; 24-bit carry
1$:     ...                  ; same for x[i+1] with e
```

The routine has an entry label every 16 elements (`dot_from_0`,
`dot_from_16`, …). A row of `n` elements is processed by placing `x`
right-aligned in the 128-byte `xvec` buffer and entering at `128 - n`. This
one routine therefore serves d_model = 48, d_ff = 96, head size 16 and the
context length 128.

`gb/src/mathasm.s` wraps it in `mv_run`, the row loop that subtracts the
two sums of squares, halves, requantizes (rounded shift + clamp) and stores
either int8 or int32 results, plus `mul16s` (16×16→32 shift-add multiply,
used by the norm and the exp scaling), `norm_scale` (the RMSNorm output
loop) and `divq` (the rounded division of the attention output).

## 5. Attention with the cache in SRAM

Per layer `l`, SRAM bank `2l` holds the K cache `[T][D]` (biased bytes)
followed by `ksq[T][H]` (uint16 sum of squares per row and head); bank
`2l+1` holds the V cache **transposed and position-reversed** `[D][T]`,
`vsq[D]` (uint32) and `vsum[D]` (int16).

Scores: for each cached position `pp`, `dot(K[pp][head], q[head])` is one
16-element call of the dot routine (rows of stride D).

Softmax: with `mx` the largest score, `d = mx - score`, the weight is
`EXP[(d * att_mul) >> 16]` where `EXP[i] = round(126 * exp(-i/16))` and
`att_mul` folds `1/sqrt(16)` and the q/k scales. Weights are 0..126, so
`e - 63` is a valid int7 and the *same* dot routine computes the weighted
sum of values: the e-vector is written reversed into `xvec` (position `pp`
at index `127 - pp`) and each transposed V row is a weight row. Because
the routine computes `sum (e-63) v`, the code adds back `63 * vsum` and
divides by `E = sum e` with `divq`. Unused positions hold biased zero so
they contribute nothing; that is why `llm_reset` fills the V bank with 63.

The reversed layout lets a partially filled context use a *shorter* entry
point of the unrolled routine (`entry = floor((127 - p) / 16) * 16`), so
early tokens cost less.

## 6. RMSNorm in integers

```
m   = max |h_i|,  s = smallest shift with (m >> s) <= 63
ss  = sum SQ7(|h_i| >> s)                      ~ rms^2 * D / 4^s      (table lookups)
r   = isqrt(ss)  (>= 1)
inv = NORM_K / r,  normalised into 16 bits by dropping e low bits
n_i = clamp( round_shift( h_i * inv, 16 + s - e ), -63, 63 )
```

with `NORM_K = 2^4 * sqrt(D) * 2^16`. Six-bit mantissas for the rms are
more than enough for an int7 output; the per-element work is one
`mul16s` and a shift, all in assembly.

## 7. Sampling

Greedy by default (argmax of the int32 logits). SELECT switches to
sampling: `EXP[((mx - logit) * LM_MUL) >> 16]` gives 7-bit probabilities
(temperature baked into `LM_MUL` at export), a 16-bit xorshift RNG seeded
from the frame counter and the DIV register picks the token. `<pad>`,
`<usr>` and `<bot>` are never emitted.

## 8. Memory and time budget (tiny model)

| | |
|--|--|
| WRAM | ~1.9 KiB: residual, activations, 128 int32 scores, 54 int32 logits, UI buffers |
| SRAM | 4 banks × 8 KiB (2 layers × K/V) |
| ROM | bank 0: 12 KiB code + 0.5 KiB table; banks 1–4: 51 KiB of weights → 128 KiB cartridge |
| Cycles per token | ~1.0 M for the matrices, +~6k per cached position for attention, ~2.3 M total at short context → ~2.5 s |

Measured with `tools/selftest.py --profile` in PyBoy, which counts frames
between checkpoints.

## 9. Verification

`llm/simulate.py` reimplements the integer pipeline in Python with the same
rounding rules (`round_shift`, `div_round`, `isqrt`, the tables from
`llm/quant.py`). `tools/selftest.py` runs a special ROM build that stops at
21 checkpoints per token and compares every buffer against the simulator;
`tools/emu_test.py` types on the real UI and compares the final text. Both
must say MATCH before a change to the engine or the exporter is merged; CI
runs the latter.

## 10. Known limitations / ideas

* ~2.5 s per character on a DMG. Remaining overhead is per-row bookkeeping
  in `mv_run` (~400 cycles/row) and the softmax loop in C; a GBC double-speed
  mode would halve wall time for free.
* Weights are 7-bit with a per-tensor power-of-two scale (about 6.5
  effective bits). Per-row scales would improve accuracy at the cost of a
  multiply per row.
* The exp table has 1/16-nat resolution and 7-bit outputs; softmax is
  approximate, which QAT does not model (measured impact: none on argmax
  for the shipped model).
* SDCC 4.4 miscompiles `CONST32 / uint16`; the code avoids that pattern
  (see the comment in `llm.c`). If you add divisions, check the generated
  assembly.
